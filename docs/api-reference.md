# API Reference

The Public Transport Spy platform provides REST endpoints for ESP32 hardware displays, web administrative interfaces, user accounts, and live transit lookups.

- **Base URL (NestJS Backend):** `http://localhost:7778`
- **Base URL (Frontend Dashboard):** `http://localhost:7777`
- **Swagger Documentation:** `http://localhost:7778/docs`
- **OpenAPI Specification (JSON):** `http://localhost:7778/docs-json`

---

## 1. Authentication & Common Headers

### 1.1 Administrative API Key (`X-Api-Key`)
Required for backend administrative endpoints (`/v1/devices/*`, `/v1/auth/user/:userName`). Set via `ADMIN_API_KEY` in environment variables:
```http
X-Api-Key: your-secret-admin-key
```
- In development/production, protected routes return `401 Unauthorized` if this header is missing or mismatched.
- The Next.js Frontend BFF automatically injects this header server-side when proxying authenticated browser requests.

### 1.2 Hardware Device Identity (`X-Device-ID`)
Sent by the ESP32 chip on all hardware client endpoints (`/api/v1/device/*`). It contains the 36-character random UUID the device generated on first boot (stored in `/id.txt`; regenerated by a factory reset):
```http
X-Device-ID: d3b07384-d113-3660-84cf-3b999cd46903
```

### 1.3 Hardware Device Token (`X-Device-Token`)
A secret 32-character authentication token issued to the device once its pairing code has been claimed, and stored locally on the chip in `/token.txt`:
```http
X-Device-Token: a8f3b92c4e1d0f8a9b7c6d5e4f3a2b1c
```
- **Never-claimed device:** `GET /api/v1/device/config` with an unrecognized `X-Device-ID` returns `404` — it is never auto-registered, since the UUID is deterministic (MD5 of a public salt + MAC) and therefore guessable. See [§2.1a](#21a-claim-device-first-time-pairing) for how a device becomes known.
- **Subsequent requests:** The backend verifies `X-Device-Token` using constant-time buffer comparison (`timingSafeEqual`). Requests without the matching token return `401 Unauthorized`.

## 2. Hardware Client Endpoints (`/api/v1/device/*`)

These endpoints are called directly by the [on-chip-software/src/main.cpp](../on-chip-software/src/main.cpp) firmware.

**Versioning:** firmware in the field hardcodes these paths (one `DEVICE_API` constant in `main.cpp`), so the version is part of the path. Additive changes (new optional response fields, new optional request fields) stay in `v1`: the firmware ignores unknown JSON fields and the backend strips unknown request properties. A breaking change ships as a new `/api/v2/device` controller **next to** v1. v1 is removed only once metrics (`firmwareVersion`) show no v1 firmware left in the field.

### 2.0 Hello (Bootstrap)
Public, unauthenticated info for a device that has no token yet.

- **Method:** `GET`
- **Path:** `/api/v1/device/hello`
- **Response (200 OK):**
  ```json
  { "pairBaseUrl": "https://app.example.com/pair" }
  ```

  **Pairing code format:** 6 characters from `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (no `0`, `1`, `O`, `I`). The API and the QR URL use it without separators (`KV79P2`); the display and the web UI show it grouped as `KV7-9P2`. `POST /v1/devices/pair` and `POST /api/v1/device/claim` accept either form (spaces, dashes and lower case are ignored) and answer `400` for anything that is not a valid code after that. Implementation: `api/src/modules/device/pairing-code.ts`, `frontend/src/helpers/pairing-code.ts`, `newPairingCode` in the firmware.

  The device builds its QR code as `pairBaseUrl + "?code=" + pairingCode`. `pairBaseUrl` comes from the `PUBLIC_APP_URL` env variable (the web app, not the API).

### 2.1a Claim Device (First-Time Pairing)
Binds this device's real hardware UUID to a pairing code an admin has already claimed in the UI. Public and unauthenticated by necessity (the device has no token yet), but only succeeds once a matching, unexpired pending claim exists — an unrecognized or not-yet-claimed code returns `404`, so a never-contacted device can never be trusted into existence just by asking.

- **Method:** `POST`
- **Path:** `/api/v1/device/claim`
- **Request Body:**
  ```json
  {
    "pairingCode": "KV79P2",
    "deviceUuid": "d3b07384-d113-3660-84cf-3b999cd46903"
  }
  ```
  *(`pairingCode` is generated locally by the firmware via `esp_random()` and displayed on the OLED before any network contact — it is the only secret that needs to stay unguessed until claimed.)*
- **Response (200 OK):**
  ```json
  {
    "stationName": "Bern",
    "timezone": "CET-1CEST,M3.5.0,M10.5.0/3",
    "theme": "standard",
    "apiInterval": 300000,
    "screenInterval": 15000,
    "metricsInterval": 600000,
    "deviceToken": "a8f3b92c4e1d0f8a9b7c6d5e4f3a2b1c",
    "isPaired": true
  }
  ```
- **Response (404 Not Found):** No admin has claimed this pairing code yet — the device should keep retrying.
- **Response (400 Bad Request):** The pairing code existed but expired (15 minutes after an admin claimed it) before the device confirmed. The device shows a new code.
- **Response (409 Conflict):** The code is already bound to a different device. The device shows a new code.
- **Response (403 Forbidden):** this hardware UUID is **registered to another account**. A UUID belongs to exactly one account; it is freed when its owner unpairs it, transfers it or deletes their account. The device shows "Registered to another account" and keeps polling, so it pairs as soon as the owner releases it. (A leftover row of the same account or one without owner is replaced.)
- **Idempotent:** a retry with the same `pairingCode` and `deviceUuid` before expiry returns the same `deviceToken` (covers a lost response). The code is cleared on the device's first authenticated `GET /api/v1/device/config`. If another row already holds `deviceUuid` (e.g. an earlier claim the device never received), that row is replaced.

### 2.1 Get Device Configuration (Poll)
Retrieve operating parameters, display font theme, timer intervals, and pairing status. Only usable by an already-claimed device.

- **Method:** `GET`
- **Path:** `/api/v1/device/config`
- **Headers:**
  - `X-Device-ID: <UUID>` (Required)
  - `X-Device-Token: <TOKEN>` (Required)
- **Response (404 Not Found):** `X-Device-ID` is not a recognized, claimed device.
- **Response (200 OK — Re-pairing, e.g. after an admin unpaired it):**
  ```json
  {
    "stationName": "Zürich HB",
    "timezone": "CET-1CEST,M3.5.0,M10.5.0/3",
    "theme": "standard",
    "apiInterval": 5000,
    "screenInterval": 15000,
    "metricsInterval": 600000,
    "isPaired": false,
    "pairingCode": "KV79P2",
    "pairingUrl": "https://app.example.com/pair?code=KV79P2"
  }
  ```
  *(Note: When `isPaired: false`, `apiInterval` is set to 5000ms so the device rapidly detects when pairing succeeds. Here the pairing code is backend-generated, since this call already required a valid `X-Device-Token` — unlike first-time pairing, there is no TOFU risk.)*
- **Response (200 OK — Paired):**
  ```json
  {
    "stationName": "Bern",
    "timezone": "CET-1CEST,M3.5.0,M10.5.0/3",
    "theme": "retro",
    "apiInterval": 300000,
    "screenInterval": 10000,
    "metricsInterval": 300000,
    "isPaired": true
  }
  ```
- **`timezone`:** always a POSIX TZ string for the firmware, converted from the device's IANA zone (e.g. `Europe/London` → `GMT0BST,M3.5.0/1,M10.5.0`; table in `api/src/modules/device/timezones/timezones.ts`).
- **Optional field `schedule`:** `{ "on": 360, "off": 1380, "days": 62 }`, present only when the owner enabled an on/off window. Minutes after local midnight (`off` may be past midnight); `days` = weekday bits, bit 0 = Sunday … bit 6 = Saturday. The window belongs to the weekday it starts on. Outside it, and while the device is disabled (403), the firmware powers the OLED down.
- **Optional field `backendBaseUrl`:** present when the `DEVICE_BACKEND_URL` env variable is set. The firmware verifies the new URL answers `GET /api/v1/device/hello` and then switches to it permanently (domain moves without reflashing).
- **Response (401 Unauthorized):** Existing device requested without a matching `X-Device-Token`.
- **Response (403 Forbidden):** The owner disabled the device (`isConfigured: false`). The device keeps its token and shows a "disabled" screen.

> The firmware treats 401/404 as "token rejected" and returns to pairing mode after 3 consecutive rejections.

### 2.2 Get Live Departures
Fetch upcoming transit departures for the station configured on this device. **Not used by current firmware** (it renders `/screens`, §2.2a); kept so v1 stays additive. Each departure may also carry `category`, `platform` and `delayMinutes`.

- **Method:** `GET`
- **Path:** `/api/v1/device/data`
- **Headers:**
  - `X-Device-ID: <UUID>` (Required)
  - `X-Device-Token: <TOKEN>` (Required)
- **Response (200 OK):**
  ```json
  {
    "station": "Zürich HB",
    "departures": [
      {
        "timestamp": 1791045840,
        "line": "S2",
        "destination": "Zürich Flughafen"
      },
      {
        "timestamp": 1791045900,
        "line": "IR 36",
        "destination": "Basel SBB"
      }
    ]
  }
  ```

### 2.2a Get Screens (customizable display)
The composed layout the firmware renders. The backend turns the owner's display profile (§5.4 `display`) and live departures into pages of positioned widgets. The device only draws them, so new presets and page types ship without a firmware update.

- **Method:** `GET`
- **Path:** `/api/v1/device/screens`
- **Headers:** `X-Device-ID`, `X-Device-Token` (required)
- **Response (200 OK, shortened):**
  ```json
  {
    "pages": [
      {
        "durationMs": 15000,
        "widgets": [
          { "t": "text", "x": 0, "y": 12, "w": 150, "font": "medium", "text": "Zürich HB" },
          { "t": "status", "x": 212, "y": 12, "align": "right" },
          { "t": "clock", "x": 254, "y": 12, "font": "medium", "align": "right", "format": "%H:%M" },
          { "t": "line", "x": 0, "y": 16, "w": 256 },
          { "t": "list", "y": 30, "rowH": 16, "maxRows": 3, "font": "regular", "leadSec": 0, "empty": "No departures scheduled right now",
            "cols": [ { "x": 0, "w": 32, "kind": "countdown" }, { "x": 34, "w": 56 }, { "x": 94, "w": 160 } ],
            "items": [ { "ts": 1780000060, "cells": ["S2", "Zürich Flughafen"] } ] }
        ]
      },
      { "durationMs": 8000, "widgets": [ { "t": "clock", "x": 128, "y": 40, "font": "xl", "align": "center", "format": "%H:%M" } ] }
    ]
  }
  ```

**Widgets** (coordinates in pixels on the 256×64 panel, `y` = text baseline, `align` = `left` | `center` | `right` relative to `x`):

| `t` | Fields | Device behavior |
|---|---|---|
| `text` | `x`, `y`, `w`, `font`, `text`, `align` | UTF-8 text, cut to `w` on whole characters |
| `clock` | `x`, `y`, `font`, `format`, `align` | Local time via `strftime` (`%H:%M`, `%a %d.%m.%Y`); `--:--` / blank until NTP synced |
| `line` | `x`, `y`, `w` or `h` | Horizontal (`w`) or vertical (`h`) rule |
| `status` | `x`, `y`, `align` | Where `[OFFLINE]` is drawn when offline or the server is unreachable; default top-right if absent |
| `list` | `y`, `rowH`, `maxRows`, `font`, `leadSec`, `empty`, `cols[]`, `items[]` | Departure rows. The device hides items more than 59 s gone or leaving sooner than `leadSec` (walking time) and moves the rest up, so the board stays correct offline. Column `kind`: `countdown` (`7'`, `Now`), `time` (`14:32`), or text = the item's next `cells` entry |

**Empty lists tell the truth:** the backend never invents departures. `empty` (drawn by the device when a list has no visible rows) is one of:
- `No departures scheduled right now`: the station genuinely has nothing coming (e.g. at night);
- `No matching departures right now`: departures exist, but the page's filters exclude them all;
- `Timetable temporarily unavailable`: the timetable provider is unreachable and no cached board is available.
While offline, the device shows its own "No Wi-Fi" hint instead.

**Fonts:** `small`, `regular`, `bold`, `medium`, `large`, `xl`, `retro` (compiled into the firmware; unknown → `regular`).

**Limits:** ≤ 6 pages, ≤ 24 widgets per page, ≤ 10 list items, list cell text ≤ 28 characters (longer text is cut by the composer; the device truncates to the column width anyway), response < 8 KB even for the largest profile with very long destination names (tested), `durationMs` 3 000 – 300 000 (enforced by the backend composer; the firmware additionally clamps to 2 s – 5 min and ignores anything beyond its limits).

**Compatibility:** unknown widget types and fields are skipped by the firmware, so new widgets can be added in v1 without breaking deployed units. The firmware keeps the last valid response in `/screens.json`; a response without pages is ignored instead of blanking the board.

**Contract test:** `api/src/modules/device/screens/screen-composer.contract.spec.ts` pins the composer output for a fixed profile into `on-chip-software/test/test_contract/screens.fixture.json`. Both renderers are tested against it with the same expectations: the firmware's native suite (`pio test -e native`, device row logic) and the web preview's logic (`npm run test:frontend`, `screen-preview-logic.ts`). After an intended composer change: `UPDATE_CONTRACT=1 npx jest screen-composer.contract`, then re-run the firmware and frontend tests.

**Ordering:** list items are sorted by actual departure time (delay included), so a late train never sits above one leaving sooner.

### 2.3 Ingest Telemetry Metrics
Receive hardware health metrics, memory usage, and Wi-Fi signal diagnostics.

- **Method:** `POST`
- **Path:** `/api/v1/device/metrics`
- **Headers:**
  - `X-Device-ID: <UUID>` (Required)
  - `X-Device-Token: <TOKEN>` (Required)
  - `Content-Type: application/json`
- **Request Body:**
  ```json
  {
    "deviceId": "d3b07384-d113-3660-84cf-3b999cd46903",
    "stationName": "Zürich HB",
    "uptimeSeconds": 1240,
    "resetReason": 1,
    "cpuFreqMHz": 240,
    "ramFreeBytes": 182400,
    "ramTotalBytes": 327680,
    "ramMinFreeEver": 164200,
    "ramMaxAllocBlock": 98304,
    "fsTotalBytes": 1507328,
    "fsUsedBytes": 45056,
    "wifiSignalRssi": -62,
    "wifiBssid": "aa:bb:cc:dd:ee:ff",
    "wifiChannel": 6,
    "firmwareVersion": "1.0.0"
  }
  ```
- **Response (200 OK):**
  ```json
  {
    "ok": true
  }
  ```
- **Response (404 Not Found):** Returned if `deviceId` does not exist in the database (squatting prevention).
- **Version skew:** unknown properties in device requests are stripped, not rejected, so firmware and backend can be updated independently.

## 3. Public Transit Endpoints (`/v1/transit/*`)

### 3.1 Live Departures Lookup
Preview live departures for any public transport station. Publicly accessible.

- **Method:** `GET`
- **Path:** `/v1/transit/departures`
- **Query Parameters:**
  - `station` (string, optional, default: `"Zürich HB"`)
  - `limit` (number, optional, default: `8`, max: `20`)
- **Response (200 OK):**
  ```json
  {
    "station": "Bern",
    "departures": [
      {
        "timestamp": 1791046200,
        "line": "IC 1",
        "destination": "Genève-Aéroport"
      }
    ]
  }
  ```

- **Response (503 Service Unavailable):** the timetable provider is down and no cached board (30 s) exists. No placeholder departures are ever returned. Each departure may also carry `category`, `platform` and `delayMinutes`.

### 3.2 Search Stations (Autocomplete)
Search Swiss railway and public transport stations by name prefix or query string. Publicly accessible.

- **Method:** `GET`
- **Path:** `/v1/transit/stations`
- **Query Parameters:**
  - `query` (string, required, min 2 chars)
  - `limit` (number, optional, default: `10`)
- **Response (200 OK):**
  ```json
  [
    {
      "id": "8503000",
      "name": "Zürich HB",
      "latitude": 47.377847,
      "longitude": 8.540502
    }
  ]
  ```

## 4. User Authentication Endpoints (`/v1/auth/*`)

### 4.1 Register Account (Public)
Creates a new user account. Unauthenticated at the start. Rate limited (`@nestjs/throttler`): 20 requests per hour.

- **Method:** `POST`
- **Path:** `/v1/auth/register`
- **Request Body:**
  ```json
  {
    "userName": "alice",
    "password": "supersecretpassword",
    "inviteCode": "secret-invite"
  }
  ```
  *(Validation: `userName` must be 3–32 lowercase alphanumeric characters with `_.-`; `password` max 72 bytes).*
- **Response (201 Created):**
  ```json
  {
    "id": "uuid-v4",
    "userName": "alice",
    "role": "USER",
    "createdAt": "2026-10-03T18:00:00.000Z"
  }
  ```

### 4.2 Login (Public)
Authenticates credentials and returns user identity. Throttled on consecutive failures.

- **Method:** `POST`
- **Path:** `/v1/auth/login`
- **Request Body:**
  ```json
  {
    "userName": "alice",
    "password": "supersecretpassword"
  }
  ```
- **Response (200 OK):** User identity object.
- **Response (401 Unauthorized):** Invalid credentials (evaluated in constant time to prevent user enumeration).

### 4.2a Usernames
Usernames are unique (stored lowercase, unique index; registering an existing name returns `409`). They identify accounts for device transfers (§5.3b).

### 4.3 Get User Profile (Protected)
Retrieves profile data for a user.

- **Method:** `GET`
- **Path:** `/v1/auth/user/:userName`
- **Header:** `X-Api-Key: <ADMIN_API_KEY>` (Required)
- **Response (200 OK):** User detail object.

### 4.4 Update User Profile (Protected)
Updates user settings or password.

- **Method:** `PATCH`
- **Path:** `/v1/auth/user/:userName`
- **Header:** `X-Api-Key: <ADMIN_API_KEY>` (Required)
- **Request Body (Partial):**
  ```json
  {
    "currentPassword": "oldpassword",
    "newPassword": "newpassword",
    "socialUrl": "https://github.com/alice",
    "avatarUrl": "https://example.com/avatar.jpg"
  }
  ```
  *(Note: Password changes require `currentPassword`. Usernames and roles cannot be changed through the API; unknown fields are stripped.)*

---

### 4.5 Delete Account (Protected)
Deletes the account after checking the password. In one transaction: pending pairing requests are removed and every display of the account is **released**: no owner, not paired, personal settings reset (name, screens, schedule). It keeps its token and shows a new backend-issued pairing code on its next poll, so its hardware UUID can be claimed by any account.

- **Method:** `DELETE`
- **Path:** `/v1/auth/user/:userName`
- **Header:** `X-Api-Key: <ADMIN_API_KEY>` (Required)
- **Request Body:** `{ "currentPassword": "..." }`
- **Response (200 OK):** `{ "releasedDevices": 2 }`
- **Response (401):** wrong password (counts towards the login rate limit). **(404):** unknown account.

## 5. Device Administration Endpoints (`/v1/devices/*`)

All `/v1/devices/*` endpoints require the `X-Api-Key: <ADMIN_API_KEY>` header. Ownership rules (one account per hardware UUID, pending requests, transfer, release on account deletion) are summarized in [architecture §1.6](architecture.md#16-device-ownership-lifecycle); every rule is covered by the database-to-API integration tests ([testing guide](testing.md)).

### 5.1 List Devices
- **Method:** `GET`
- **Path:** `/v1/devices`
- **Query Parameter:** `userId` (optional filter)
- **Response (200 OK):** Array of `DeviceDetailDto` objects. `deviceToken` and expired pairing codes are never included.

### 5.1a Supported Time Zones
- **Method:** `GET`
- **Path:** `/v1/devices/timezones`
- **Response (200 OK):** array of IANA names (`["UTC", "Europe/London", …, "America/Los_Angeles"]`) accepted by `PATCH` (§5.4) and offered by the web app's picker.

### 5.2 Get Device by UUID
- **Method:** `GET`
- **Path:** `/v1/devices/:uuid`

### 5.3 Pair Device (Claiming)
Claims the 6-character code currently displayed on a device's screen for the authenticated user. The device does not need to have contacted the backend yet.
- **Method:** `POST`
- **Path:** `/v1/devices/pair`
- **Header:** `X-Api-Key: <ADMIN_API_KEY>` (Required)
- **Request Body:**
  ```json
  {
    "pairingCode": "KV79P2",
    "userId": "alice",
    "name": "Living Room Display",
    "stationName": "Bern"
  }
  ```
- **Response (200 OK, device never contacted the backend before):** A pending device record with `deviceUuid: null` and `isPaired: false`, bound to `userId`. The physical device becomes fully paired once it calls `POST /api/v1/device/claim` with this code (see §2.1a).
- **Response (200 OK, device already known, e.g. re-pairing after an unpair):** Device details object with `isPaired: true` immediately — the pairing code is consumed and cleared.
- **Cleanup:** expired pending claims (rows with no `deviceUuid`) are deleted on every pair call and every device listing (§5.1), so a mistyped code never blocks a future one or lingers as "Pending".
- **Response (409 Conflict, pending code of another account):** a pending request (no hardware UUID yet) belongs to the account that entered the code first; another account cannot take it over. Unpaired devices (hardware UUID set, owner cleared) remain claimable with their current code.
- **Response (409 Conflict):** This pairing code has already been claimed by another pairing request.

### 5.3b Transfer a Display to Another Account
Hands a paired display to another account by username. It stays paired, keeps its token and settings and keeps running; only the owner changes.

- **Method:** `POST`
- **Path:** `/v1/devices/:uuid/transfer`
- **Request Body:** `{ "toUserName": "bob", "fromUserName": "alice" }` (`fromUserName` must be the current owner; the BFF fills it from the session)
- **Response (200 OK):** `DeviceDetailDto` of the new owner.
- **Response (400):** target is the current owner. **(404):** unknown/unpaired display, caller is not the owner, or no account with `toUserName` (message says which).

### 5.3a Cancel a Pending Pairing Request
Removes the owner's pending request (e.g. a mistyped code). Pending requests have no hardware UUID yet, so this is the only route addressed by the row's internal id; it can never delete a claimed device, which stays addressable only by its hardware UUID.

- **Method:** `DELETE`
- **Path:** `/v1/devices/pending/:id?userId=<userName>`
- **Response (204 No Content):** removed.
- **Response (400):** `id` is not a UUID, or `userId` is missing.
- **Response (404):** no pending request with this id for this user (also for claimed devices and other users' requests).

### 5.4 Update Device Configuration
- **Method:** `PATCH`
- **Path:** `/v1/devices/:uuid`
- **Request Body (Partial):**
  ```json
  {
    "name": "Kitchen Clock",
    "stationName": "Basel SBB",
    "theme": "retro",
    "timezone": "Europe/Zurich",
    "isConfigured": true,
    "scheduleEnabled": true,
    "scheduleOn": 360,
    "scheduleOff": 1380,
    "scheduleDays": 62,
    "apiInterval": 120000,
    "screenInterval": 10000,
    "metricsInterval": 300000,
    "display": {
      "pages": [
        { "type": "departures", "rows": 4, "showPlatform": true, "showDelay": true, "categories": ["S"], "walkMinutes": 3 },
        { "type": "departures", "station": "Bern", "title": "To Bern", "lines": ["IC 1"], "timeFormat": "clock" },
        { "type": "clock", "showDate": true, "durationSec": 5 },
        { "type": "message", "text": "Gone fishing\nBack Monday" }
      ]
    }
  }
  ```
- **`timezone`**: one of the supported IANA zones (§5.1a); anything else (including raw POSIX strings) is `400`.
- **`isConfigured`**: `false` switches the display off (device gets `403` and blanks its panel).
- **Schedule**: `scheduleEnabled`, `scheduleOn`/`scheduleOff` (0–1439 minutes after local midnight; `off < on` = overnight), `scheduleDays` (1–127, bit 0 = Sunday).
- **`display`** (optional; `null` resets to the default departures board): 1–6 pages, shown in rotation.

  | Page `type` | Options |
  |---|---|
  | all | `durationSec` 3–300 (default 15 for departures, 8 otherwise) |
  | `departures` | `station` (default: device station), `title` (header, ≤ 40), `rows` 1–4, `timeFormat` `countdown` \| `clock`, `showPlatform`, `showDelay`, `lines[]` (only these; spaces/case ignored), `excludeLines[]`, `categories[]` (S, IR, IC, B, T, …), `destinationContains`, `walkMinutes` 0–60 |
  | `clock` | `showDate` |
  | `message` | `text` (required, ≤ 120 chars, up to 3 lines split by `\n`) |

  Invalid profiles return `400` and leave the stored profile unchanged. The device's `theme` still applies (fonts chosen by the composer).

### 5.4a Preview Screens (unsaved settings)
Composes the screens exactly as the device would receive them (§2.2a), from settings that are **not saved yet**. Used by the web app's live preview. Saves nothing.

- **Method:** `POST`
- **Path:** `/v1/devices/:uuid/screens/preview`
- **Request Body (all optional; omitted fields use the stored values):**
  ```json
  { "display": { "pages": [{ "type": "departures", "rows": 4 }] }, "stationName": "Bern", "theme": "retro" }
  ```
- **Response (200 OK):** same shape as `GET /api/v1/device/screens`.
- **Response (400):** the draft fails the same validation as a save (e.g. `display.pages.1.text must contain visible characters`).
- **Response (404):** unknown device.

### 5.5 Unpair Device
- **Method:** `POST`
- **Path:** `/v1/devices/:uuid/unpair`
- **Response (200 OK):** Device details object with `isPaired: false`.

### 5.6 Inspect Device Telemetry History
- **Method:** `GET`
- **Path:** `/v1/devices/:uuid/metrics?limit=50`
- **Who sees it:** only administrators, through the web app's admin dashboard (`/admin`, BFF routes `/api/v1/admin/*`). Display owners no longer see telemetry.
- **Response (200 OK):** Array of `DeviceMetricDto`, newest first. Ids are UUIDv7; all byte/uptime values are numbers (never strings). The entity and its device relation are never returned.

## 6. Frontend BFF Endpoints (`frontend/src/app/api/v1/*`)

Browser clients interact with the Next.js Route Handlers. The BFF manages session cookies and transparently injects `X-Api-Key` to the NestJS backend. "Admin" routes additionally check the user's role **via the API on every request** (`verifyAdminSession()`), never from the cookie:

| Method | Path | Requires Auth | Description |
|---|---|---|---|
| `POST` | `/api/v1/user` | No | Log in and establish encrypted `session` cookie. |
| `PUT` | `/api/v1/user` | No | Register new user and establish session cookie. |
| `GET` | `/api/v1/user` | Yes | Get current authenticated user session and profile. |
| `PATCH` | `/api/v1/user` | Yes | Update current user profile or password. |
| `DELETE` | `/api/v1/user` | No | Clear session cookie (logout). |
| `GET` | `/api/v1/devices` | Yes | Fetch devices owned by the current session user. |
| `POST` | `/api/v1/devices` | Yes | Pair device with current user (`pairingCode`, `name`, `stationName`). |
| `GET` | `/api/v1/devices/:uuid` | Yes | Fetch device settings for owner. |
| `PATCH` | `/api/v1/devices/:uuid` | Yes | Update display settings. |
| `DELETE` | `/api/v1/devices/:uuid` | Yes | Unpair device. |
| `DELETE` | `/api/v1/user/account` | Yes | Delete the session user's account (`{ currentPassword }`), release their displays and log out (proxies §4.5). |
| `POST` | `/api/v1/devices/:uuid/transfer` | Yes | Transfer the session user's display to `{ toUserName }` (owner checked by BFF and API, proxies §5.3b). |
| `DELETE` | `/api/v1/devices/pending/:id` | Yes | Cancel the session user's pending pairing request (proxies §5.3a with the session's username). |
| `GET` | `/api/v1/devices/timezones` | Yes | Supported time zones for the settings picker (proxies §5.1a). |
| `GET` | `/api/v1/admin/devices` | Admin | All devices of all owners (admin telemetry dashboard). `403` for non-admins. |
| `GET` | `/api/v1/admin/devices/:uuid/metrics` | Admin | Telemetry history (`?limit=` 1–500). `403` for non-admins. |
| `POST` | `/api/v1/devices/:uuid/screens/preview` | Yes | Live preview: compose unsaved `display`/`stationName`/`theme` for the owner (proxies §5.4a). |
| `GET` | `/api/v1/transit/stations` | No | Proxy station autocomplete lookups. |
