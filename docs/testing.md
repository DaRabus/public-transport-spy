# Testing Guide

Every layer has its own suite, and CI runs all of them (see [CI](#ci) below).

| Suite | Command | What it proves | Needs |
|---|---|---|---|
| API unit | `npm run test:api` | Services, composer, guards, DTO mapping, time zones, contract fixture pin | nothing |
| API end-to-end | `npm --prefix api run test:e2e` | HTTP pipeline (guard, validation, controllers, composer) with in-memory repositories | nothing |
| **API integration** | `npm run test:integration` | **Database to API**: real `AppModule`, real TypeORM + migrations on PostgreSQL 18, driven over HTTP | PostgreSQL 18 |
| Web app logic | `npm run test:frontend` | Live-preview rendering rules, admin metrics shaping, pairing-code format (`*.test.ts` run by `node:test`, no extra deps; typechecked first with `frontend/tsconfig.test.json`, which the app's `tsconfig.json` excludes) | nothing |
| Firmware logic + contract | `cd on-chip-software && pio test -e native` | Device decision logic, schedule, and rendering of the backend-pinned screen fixture | PlatformIO |
| Migration drift | `npm run migration:check` | Entities and migrations agree (every schema change has a migration) | a migrated database (`DATABASE_URL`) |

## API integration tests (database to API)

Location: `api/test/integration/*.int-spec.ts`, harness in `integration-app.ts`.

- **What is real:** the whole Nest application (`AppModule` with `AdminApiKeyGuard`, global validation, all services and controllers), TypeORM, the migrations and PostgreSQL 18 (constraints, `uuidv7()`, `jsonb`, transactions).
- **What is stubbed:** only the external timetable provider (`TransitService`), so results are deterministic and no test hits the internet.
- **Database:** `INTEGRATION_DATABASE_URL`, defaulting to a dedicated `public_transport_spy_test` database on the local `pts-postgres` container (`localhost:4700`). The harness creates it if missing, runs the migrations, and truncates all tables before each test. It sets its own env vars, which take precedence over `api/.env`, so the development database is never touched.
- **Run locally:**
  ```bash
  docker compose up -d pts-postgres
  npm run test:integration
  ```
- **CI:** a `postgres:18-alpine` service container; the workflow sets `INTEGRATION_DATABASE_URL`.

### Covered behaviour

`device-ownership.int-spec.ts`
- usernames are unique (case-insensitive); primary keys are UUIDv7 generated by the database;
- one account per hardware UUID: a claim for a UUID owned by another account gets `403` and changes nothing; the same account's leftover row is replaced; the unique index enforces it in the schema;
- an account can own several displays;
- pending pairing requests: first account wins (`409` for others), only the owner can cancel (never a claimed display), expired ones disappear on the next listing;
- transfer by username: the display stays paired and keeps working with its token; unknown users, self-transfer and non-owners are refused;
- account deletion: wrong password changes nothing; with the password the account and its pending requests are removed, displays are released with their personal settings cleared, telemetry stays, the display gets a fresh pairing code and another account can claim the same hardware UUID.

`device-settings.int-spec.ts`
- device authentication (token, unknown device `404`, switched-off display `403`);
- IANA time zone and schedule round-trip, POSIX string and `schedule` sent to the device; invalid settings leave the stored ones untouched;
- the `jsonb` screen profile is persisted and composed (filters, platform, delay, rows);
- honest empty boards ("No departures scheduled right now", "Timetable temporarily unavailable");
- telemetry: values come back as numbers, out-of-range values get `400`, as a DTO without relations, unknown fields from newer firmware are stripped; unknown devices get `404`.

### Writing a new integration test

```typescript
const ctx = await createIntegrationApp();           // beforeAll
const api = apiClient(ctx.app);
await resetDatabase(ctx.dataSource);                // beforeEach
await api.register('alice');
const token = await api.adoptDevice('alice', 'ANKA22', randomUUID()); // pair + claim
await api.deviceConfig(uuid, token).expect(200);
ctx.transit.getDepartures.mockResolvedValue([...]); // control the timetable
```

Check new tests can fail: temporarily break the rule they cover (runtime change, not a compile error) and confirm the suite goes red.

## Contract fixture (backend ↔ firmware ↔ web preview)

`api/src/modules/device/screens/screen-composer.contract.spec.ts` pins the composer output for a fixed profile into `on-chip-software/test/test_contract/screens.fixture.json`. The firmware (`pio test -e native`) and the web preview (`npm run test:frontend`) render that same file with the same expectations. After an intended composer change: `UPDATE_CONTRACT=1 npx jest screen-composer.contract` (in `api/`), then re-run both.

## Migration drift check

`npm run migration:check` runs TypeORM's `migration:generate --check` against a fully migrated database. It exits non-zero if the entities need a migration that doesn't exist yet. Locally, after the integration tests:

```bash
DATABASE_URL=postgres://postgres:postgres@localhost:4700/public_transport_spy_test npm run migration:check
```

## CI

| Workflow | Runs on | Checks |
|---|---|---|
| `[CI]-test-integration.yaml` | every PR, push to `main` | API unit → API end-to-end → API integration (PostgreSQL 18 service container) → migration drift check → web app logic tests |
| `[CI]-build-pr.yaml` | every PR, push to `main` | Prettier check, API typecheck + build, frontend build (includes its typecheck), **Docker images** for API and frontend (same contexts as `docker-compose.yml`, so lockfile/Dockerfile drift fails), and a **stack smoke test** that boots PostgreSQL + API + frontend with `docker compose` and probes health, the proxy and the auth guards |
| `[CI]-firmware-stats.yaml` | changes in `on-chip-software/` or the workflow | firmware logic + contract tests, dev build with RAM/flash report (PR comment), **retail build**, and a check that the retail build refuses to compile without `PTS_BACKEND_URL` |
| `[CI]-pr-size.yaml` | every PR | size label |

The contract fixture lives in `on-chip-software/`, so regenerating it after a composer change also triggers the firmware workflow; a composer change without a regenerated fixture already fails the API unit tests.

## Automated dependency updates (Renovate)

[`.github/renovate.json5`](../.github/renovate.json5) keeps dependencies current with little work:

- **Merges itself:** minor and patch updates of npm packages, GitHub Actions, Docker base images and `.nvmrc`, three days after release, plus a weekly lockfile refresh. Renovate merges only when every check above is green.
- **Needs a human:** major versions (separate PR, 14-day wait), PostgreSQL and Node majors (disabled, because they need a data migration or a deliberate runtime change), and everything under `on-chip-software/` (firmware libraries are compile-tested only; flash a board before merging). Security fixes arrive immediately and are never auto-merged.
- **One-time setup:** install the [Renovate GitHub app](https://github.com/apps/renovate) on the repository. Then protect `main` (Settings → Branches) and require the checks `Build NestJS API`, `Build Next.js Frontend`, `Docker Images`, `Stack Smoke Test` and `Jest Unit & Integration Tests`, so nothing, Renovate included, merges without them. `Firmware Compilation & Memory Stats` only runs for firmware changes, so leave it optional.
- **What the checks cover:** the unit, end-to-end and PostgreSQL integration tests prove behaviour; the smoke test proves the updated dependencies still start and talk to each other. Two things stay manual: the ESP32 on real hardware, and the live timetable provider. If an update ever slips through broken, add the missing case to the matching suite so the next one is caught.
